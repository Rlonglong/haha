# 15 · 新增或調整處理節點

**什麼時候需要這篇**:現有的六個階段(下載 → 檔規 → 加密 → 清洗 → 入庫 → 封存)
不夠用,要在中間插一個新階段。例如「入庫前先做資料品質檢核」。

**檔案**:`dagster_code/assets.py::build_table_assets`

---

## 一、現在的邏輯是什麼

### 1-1 節點是動態產生的

`build_table_assets(table_name, config)` 是一個工廠函式,依 config 決定要建立哪些資產:

```python
all_table_assets = []
for tbl, cfg in TABLE_CSV_MAPPING.items():
    all_table_assets.extend(build_table_assets(table_name=tbl, config=cfg))
```

每個節點的建立條件:

| 節點 | 條件 |
|---|---|
| `*_fetch_ftp` | `use_ftp_fetch` |
| `*_named` | `use_data_rule` |
| `*_encrypted` | `encrypt_fields` 非空 |
| `*_clean` | `has_clean_func` |
| `database/*` | 無條件 |
| `*_archive_cleanup` | `use_ftp_fetch` |

### 1-2 相依關係是「往前找第一個有開的節點」

這是整個設計的核心。以清洗節點為例:

```python
            deps=(
                [encrypt_asset_key] if encrypt_fields
                else ([named_asset_key] if use_data_rule
                    else ([fetch_asset_key] if use_ftp_fetch else []))
            ),
```

意思是:有加密就接加密,沒加密就接檔規,再沒有就接下載,都沒有就沒有上游。

入庫節點的判斷更長,因為它要往前找四層:

```python
        deps=(
            [clean_asset_key] if has_clean_func
            else ([encrypt_asset_key] if encrypt_fields
                else ([named_asset_key] if use_data_rule
                        else ([fetch_asset_key] if use_ftp_fetch else [])))
        ),
```

### 1-3 檔名也是層層推導的

每個節點自己算出「上一階段的產物在哪」:

```python
            if use_data_rule:
                raw_csv_path = f"~/{staging_subfolder}/{actual_csv_name.replace('.csv', '_NAMED.csv')}"
            elif use_ftp_fetch:
                raw_csv_path = f"~/{staging_subfolder}/{actual_csv_name}"
            else:
                raw_csv_path = os.path.join(in_dir, actual_csv_name)
```

**同樣的推導邏輯散在好幾個節點裡**,這是目前最容易改錯的地方。

### 1-4 還有三個地方也在推導同一套節點清單

| 位置 | 用途 |
|---|---|
| `assets.py::build_table_assets` | **真正建立節點**(唯一來源) |
| `sensors.py::_watch_files_and_build_requests` | sensor 要送出的 asset_selection |
| `selections.py::build_el_asset_keys` | 排除 `manual_only` 的表用 |

**新增節點時這三處都要改,否則會出現「節點存在但 sensor 不會觸發它」之類的怪現象。**

## 二、想調什麼,改哪裡

### 調整 A:新增一個處理階段

假設要在「清洗」之後、「入庫」之前加一個 `*_validate`(資料品質檢核)。

#### 步驟 1:在 `build_table_assets` 開頭讀設定與定義 key

```python
    use_validate = config.get("use_validate", False)
    ...
    validate_asset_name = f"{table_name}_validate"
    validate_asset_key = AssetKey(["file_system", validate_asset_name])
```

#### 步驟 2:在清洗節點之後、入庫節點之前插入新節點

```python
    # ==========================================
    # 節點 1.D-2：資料品質檢核
    # ==========================================
    if use_validate:
        @asset(
            key_prefix=["file_system"],
            name=validate_asset_name,
            partitions_def=target_partitions_def,
            group_name=target_group,
            compute_kind="validation",
            retry_policy=my_retry_policy,
            deps=(
                [clean_asset_key] if has_clean_func
                else ([encrypt_asset_key] if encrypt_fields
                    else ([named_asset_key] if use_data_rule
                        else ([fetch_asset_key] if use_ftp_fetch else [])))
            ),
            pool=validate_asset_name,
        )
        def _validate_asset(context: AssetExecutionContext, ssh_pipes: PipesSSHClient) -> MaterializeResult:
            partition_date = context.partition_key
            formatted_date = partition_date.replace("-", "") if freq == "daily" else partition_date.replace("-", "")[:6]
            actual_csv_name = csv_filename_template.format(date=formatted_date)

            # 跟入庫節點用同一套「來源檔在哪」的推導
            if has_clean_func:
                target_csv_path = os.path.join(out_dir, actual_csv_name.replace(".csv", "_CLEAN.csv"))
            elif encrypt_fields:
                target_csv_path = os.path.join(in_dir, actual_csv_name.replace(".csv", "_ENCRYPTED.csv"))
            else:
                target_csv_path = os.path.join(in_dir, actual_csv_name)

            result = ssh_pipes.run(
                context=context,
                command=[
                    "python3.11", "/home/bcp_runner/scripts/validate_remote.py",
                    "--input", target_csv_path,
                    "--table", table_name,
                ],
            )
            return result.get_results()

        assets_for_this_table.append(_validate_asset)
```

#### 步驟 3:把入庫節點的 `deps` 接到新節點

### 調整 B:改某個節點的中繼檔名

例如把 `_CLEAN.csv` 改成 `_CLEANED.csv`。

**要一起改的地方**(用 `grep -n "_CLEAN" dagster_code/assets.py` 找):

1. 清洗節點裡的 `clean_csv_name`
2. 入庫節點裡推導來源檔的那一段
3. 封存節點裡(如果有用到)

**漏改任何一處,下游就會找不到檔案。**

> 這種散落的字串是目前的技術債。要根治的話,可以抽一個
> `def _stage_paths(table_name, config, partition_date) -> dict` 統一產出所有階段的路徑,
> 讓所有節點都跟它拿。**但那是比較大的重構,不要在趕時間時做。**

`deps` 會自動往前接。

## 三、改完怎麼驗證

1. 語法檢查 → Reload code location
2. **Assets** 頁面確認:
   - 新節點出現,群組正確
   - 相依圖上,新節點的上游與下游都接對了
3. 手動 materialize 整條鏈的每個節點,確認檔案一路傳下去
4. **看 sensor tick log**:觸發時送出的 asset_selection 有沒有包含新節點
   (這是最容易漏的——節點建好了但 sensor 不會觸發它)
5. 如果有 `manual_only` 的表,確認新節點也被排除在批次 job 外

## 四、注意事項

| 事項 | 說明 |
|---|---|
| **三處推導必須同步** | `assets.py`(建立)、`sensors.py`(觸發)、`selections.py`(排除)。這是目前的架構弱點 |
| **`deps` 的巢狀三元式很容易改錯** | 加一層就多一層括號,改完務必看相依圖確認 |
| **每個節點都要有 `pool=`** | 少了的話會用預設池,可能造成同一張表並行 |
| **`key_prefix` 決定 UI 分類** | 檔案類用 `["file_system"]`,入庫用 `["database"]`,匯出用 `["export"]` |
| **新節點要不要 retry_policy** | 網路/IO 類的建議帶,純運算類的可以不帶 |
