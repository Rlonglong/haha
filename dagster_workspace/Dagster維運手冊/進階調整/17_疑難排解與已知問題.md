## 一、症狀對照表

### Code location 相關

| 症狀 | 原因 | 處理 |
|---|---|---|
| `IndentationError` | 手改程式時縮排跑掉,或 Tab 混空白 | 用 `python3 -m py_compile` 先檢查;編輯器設定成「Tab 轉空白」 |
| `AttributeError: ... has no attribute 'xxx'` | 用到這個 dagster 版本沒有的 API | 查該版本的可用 API,或改用版本無關的寫法 |
| `設定值不合法：xxx` | 表名/索引名等不符合白名單 | 改名,不要放寬白名單 |
| `必須提供 archive_dir` | 開了 `use_ftp_fetch` 但沒給封存目錄 | 補上設定 |
| `ftp_remote_dir 與 ftp_remote_filename_prefix 必須同時提供` | 只給了一個 | 兩個一起給,或改用 `ftp_remote_template` |
| `No such file or directory: .../manifest.json` | CI/CD 沒產生 manifest | 先看 GitLab pipeline 是不是紅的;真的要手動產見 [04 · 附註](../日常維運/04_新增一支dbt模型.md#附註--手動產生-manifest-與編譯-sql) |
| Reload 逾時 | 載入時要解析 manifest,模型多了會變慢 | 調大 `dagster.yaml` 的 `code_servers.reload_timeout` |

### dbt 相關

| 症狀 | 原因 | 處理 |
|---|---|---|
| 新模型在 UI 上看不到 | manifest 沒重產(CI/CD 沒跑或失敗) | 確認 pipeline 綠燈 → Reload definitions |
| 模型有出現但永遠不執行 | `tags` 少了 `daily_job` / `monthly_job` | 補 tag → push → Reload definitions |
| 月頻模型顯示成功但沒資料 | 月線固定下 `dbt snapshot`,不跑一般模型 | 見下方「已知問題 2」 |
| `Env var required but not provided: 'DBT_DB_PASSWORD'` | `.env` 沒設好,或改了 `docker_pipes` 的 env 傳遞 | 檢查 `dagster_code/.env` 的 `DB_USER` / `DB_PASS` |
| 增量重跑資料變兩倍 | 沒設 `incremental_strategy`,走 append | 改用 `delete+insert` + `unique_key`,或重跑前先刪當日資料 |
| `Compilation Error ... source 'database.XXX' not found` | 來源表沒在 `sources.yml` 登記 | 補登記 |
| 執行順序不對 | 模型裡寫死表名而不是用 `ref()` | 改用 `ref()`,並用 Lineage 分頁確認連線有出現 |
| `'dict object' has no attribute 'outwardthreshold'` | `is_outward_large` 用在沒定義該 key 的代號上 | 見下方「已知問題 1」的殘留問題 |
| 代碼清單改了但某支模型沒跟著變 | 那支模型自己複製了一份,沒走 `get_config()` | 改成引用 `get_config()`(見 [04 · Step 1-B](../日常維運/04_新增一支dbt模型.md#step-1-b--善用-macros不要自己重打一長串代碼)) |

### 檔案線相關

| 症狀 | 原因 | 處理 |
|---|---|---|
| 檔案已到但 sensor 沒反應 | ①未滿 60 秒穩定期 ②檔名沒有 8/6 碼日期 ③副檔名不符 ④已在 cursor 裡 | 看 sensor tick log 的「監控目錄 / 找到」訊息 |
| 同一天想重跑但 sensor 不理 | run_key 已處理過 | Reset cursor,或直接手動 materialize |
| BCP 成功但資料庫沒資料 | BCP 進的是 `bcp_target` 指的 View | 查 `<output_folder>/bcp_error_logs/` |
| `找不到 XXX 的清洗邏輯` | VM1 的 `CLEAN_FUNC_MAP` 沒註冊 | 到 VM1 補註冊(見 [03_新增一張資料表](../日常維運/03_新增一張資料表.md#3-1-清洗函式只有設了-has_clean_func-true-才需要)) |
| 檔名日期變成 6 碼 | `freq` 沒填,被當成月檔 | 補 `freq: "daily"` |
| SSH 逾時 | 單次指令超過 7200 秒 | 調 `timeout_seconds`,或把工作拆批 |
| 兩個分區卡住不動 | 池上限 1,前一個還沒跑完 | Runs 頁面看有沒有 Run 卡在 STARTED |
| 抓到寫到一半的檔案 | `FILE_STABLE_SECONDS` 太小 | 調大到 120–300 |

### 匯出相關

| 症狀 | 原因 | 處理 |
|---|---|---|
| 匯出不會自動觸發 | `depends_on_dbt_model` 填成 alias 而不是檔名 | 改成模型檔名 |
| 查無此表 | `source_table` 填成檔名而不是 alias | 改成資料庫實體表名 |
| CSV 用 Excel 開亂碼 | 編碼沒有 BOM | `encoding: "utf-8-sig"` |
| 檔案落地了但不該落地 | 設了 `keep_local_copy: True` | 移除該設定 |

## 二、已知問題

### 問題 1:~~`macros/` 不在版控裡~~ ✅ 已解決

`dbt_project/macros/` 已納入版控,包含:

| 檔案 | 內容 |
|---|---|
| `anti_fraud/config.sql` | `get_config()`——交易代碼清單與金額門檻的註冊表 |
| `anti_fraud/logic.sql` | `is_inward_all` / `is_inward_large` / `is_outward_all` / `is_outward_large` / `is_atm_outward_all` |
| `global/math_utils.sql` | `safe_divide` 除法防呆 |
| `global/override_temp_relation.sql` | `make_temp_relation`——暫存表名加上 invocation_id 避免撞名 |

用法見 [04 · Step 1-B](../日常維運/04_新增一支dbt模型.md#step-1-b--善用-macros不要自己重打一長串代碼)。

**殘留的小問題**:`is_outward_large` 讀的 key 是 `outwardthreshold`(沒底線),
而 `is_inward_large` 讀的是 `inward_threshold`(有底線)。目前只有 `VIRTUAL_TRANSACT`
定義了 `outwardthreshold`,**對其他代號呼叫 `is_outward_large` 會在編譯時出錯**。
要統一命名的話,`config.sql` 與 `logic.sql` 兩邊要一起改。

### 問題 2:月線只能跑 snapshot 🟠

`post_office_dbt_monthly_assets` 呼叫 `_run_dbt_levels(..., is_snapshot=True)`,
實際下的指令是 `dbt snapshot`。

目前 `monthly_job` tag 只出現在兩支 snapshot 上,所以沒事;
但**只要有人新增一支 `tags=["monthly_job"]` 的一般模型,
Dagster 會標成成功卻完全沒有執行。**

修正方式見 [13_dbt執行行為 · 調整 E](./13_dbt執行行為.md#調整-e★支援月頻的一般模型目前的限制)。

---

### 問題 3:snapshot 的 asset key 可能帶 schema 前綴 🟡

`selections.py` 用 `AssetKey([node["name"]])` 組月檔選集,
但 snapshot 設了 `target_schema='snapshots'`,dagster-dbt 預設會把 config 裡的 schema
併進 asset key。

**如果發現 `__MONTHLY_ASSET_JOB` 選不到 snapshot、或 UI 上 snapshot 的 key 是
`snapshots/snp_cust`,這裡就是第一個要檢查的地方。**

---

### 問題 4:FTP 節點的例外處理有未定義名稱 🟠

`assets.py::_fetch_ftp_asset` 裡:

```python
            except PipesSubprocessError as e:
                if getattr(e, "exit_code", None) == 99:
                    context.log.info("FTP 檔案尚未到齊，本次排程安全略過 (Skip)")
                    return SkipReason("FTP 檔案尚未到齊")
                raise
```

`PipesSubprocessError` 與 `SkipReason` **在 `assets.py` 都沒有 import**。

**後果**:只要遠端腳本真的回傳 exit code 99,這段會直接 `NameError`,
「檔案未到齊 → 安全略過」的設計等於沒有生效。
(而且 asset 函式本來就不能 `return SkipReason`。)

**修正方向**:改在 sensor 層判斷檔案是否齊全,或讓遠端腳本回 0 並用 metadata 標示狀態。

### 問題 5:節點清單在三個地方各推導一次 🟡

| 位置 | 用途 |
|---|---|
| `assets.py::build_table_assets` | 真正建立節點 |
| `sensors.py::_watch_files_and_build_requests` | sensor 的 asset_selection |
| `selections.py::build_el_asset_keys` | 排除 `manual_only` |

**新增節點時三處都要改**,漏了會出現「節點存在但 sensor 不會觸發它」。
詳見 [15_新增或調整處理節點](./15_新增或調整處理節點.md)。

### 問題 6:中繼檔名的字串散落各處 🟡

`_NAMED.csv`、`_ENCRYPTED.csv`、`_CLEAN.csv` 這些後綴在多個節點裡各自拼一次。
改檔名規則時漏改一處,下游就找不到檔案。

**根治方向**:抽一個統一產出所有階段路徑的函式,讓所有節點跟它拿。

### 問題 7:`slack_failure_alert` 沒有真的送通知 🟡

名字叫 slack,但實際上只有 `context.log.error(...)`,沒有任何外送邏輯。

### 問題 8:檔名日期用 `re.search` 抓第一段 🟡

`date_regex=r'(\d{8})'` 抓的是檔名裡第一段 8 碼數字。
檔名如果同時含有其他 8 碼數字(例如 `T_20240101_20260801.csv`),會抓錯。

目前的檔名規則沒有這個問題,但新增表時要留意。
修正方式見 [10_Sensor掃描頻率與觸發邏輯 · 調整 E](./10_Sensor掃描頻率與觸發邏輯.md#調整-e改檔名的日期解析規則)。

## 三、除錯時的順序建議

```
1. 先看 Dagster UI 的 Run log（狀態、哪一步失敗）
      ↓ 需要細節
2. 看明細 log（路徑、遠端指令、遠端輸出）
   grep "run=<Run ID>" /app/workspace/dagster_home/logs/pipeline_detail.log
      ↓ 沒有結論
3. 看 VM1 上的實際檔案：檔案在不在？大小合理嗎？內容對嗎？
      ↓ 沒有結論
4. dbt 問題 → 看 target/compiled 的 SQL，複製到 SSMS 手跑
   檔案問題 → 到 VM1 手動執行同一條指令（明細 log 裡有完整指令）
      ↓ 沒有結論
5. 看 sensor 的 tick log：是不是根本沒被觸發？
      ↓ 沒有結論
6. 看 code location 狀態：是不是根本沒載入成功？
```

**明細 log 裡的 SSH 指令可以直接複製到 VM1 上手動執行**,這是最有效的除錯手段:

```
2026-08-05 14:22:31 INFO [run=... asset=... partition=...] SSH → 10.10.159.74 指令: python3.11 /home/bcp_runner/scripts/clean_remote.py --input ... --output ...
```

> ⚠️ UI 上已經看不到這些內容,見 [18_Log分流與資安](./18_Log分流與資安.md)。
