# 12 · 併發、重試、資源池

**檔案**:`dagster_home/dagster.yaml`、`dagster_code/assets.py`、`dagster_code/sensors.py`

---

## 一、現在的邏輯是什麼

### 1-1 併發控制有三層

```
第一層：同時最多幾個 Run
    dagster.yaml → max_concurrent_runs: 5

第二層：每個資源池(pool)同時最多幾個 op
    dagster.yaml → default_op_concurrency_limit: 1

第三層：每個資產屬於哪個池
    assets.py → 每個 @asset 都帶 pool=<自己的名字>
```

**合起來的效果**:最多 5 個 Run 同時跑,但**同一個資產絕對不會並行**
(因為每個資產獨佔一個池,而池的上限是 1)。

這是為了避免同一張表的兩個日期同時 BCP 進同一張資料表。

```yaml
# dagster_home/dagster.yaml
run_coordinator:
  module: dagster.core.run_coordinator
  class: QueuedRunCoordinator
  config:
    max_concurrent_runs: 5

concurrency:
  default_op_concurrency_limit: 1
```

### 1-2 重試有四層

| 層級 | 設定在哪 | 目前值 | 行為 |
|---|---|---|---|
| **資產層** | `table_mapping.py` 各表的 `retries` / `retry_delay_sec` | 多數表 `3` 次 / `60` 秒 | 該資產失敗後自己重試 |
| **Run 層** | sensor 送出 RunRequest 時帶的 tag | `max_retries: 3`,策略 `FROM_ASSET_FAILURE` | 整個 Run 失敗後重跑,**只跑失敗的資產** |
| **dbt 層內建** | `assets.py::_run_dbt_levels` | 每層 `2` 次 / 間隔 `30` 秒 | dbt 的某一層失敗就重試那一層 |
| **SSH 逾時** | `pipes_ssh_client.py` | `7200` 秒 | 單一 SSH 指令的上限 |

資產層:

```python
    max_retries = config.get("retries", 0)
    delay_sec = config.get("retry_delay_sec", 60)
    my_retry_policy = RetryPolicy(max_retries=max_retries, delay=delay_sec) if max_retries > 0 else None
```

> **`retries` 沒填或填 0 = 完全不重試**(`RetryPolicy` 是 `None`)。

Run 層(在 sensor 裡):

```python
                tags={
                    "dagster/max_retries": "3",
                    "dagster/retry_strategy": "FROM_ASSET_FAILURE",
                },
```

dbt 層:

```python
    max_retries = 2
    retry_delay = 30
```

## 二、想調什麼,改哪裡

### 調整 A:讓系統同時跑更多 Run

```yaml
# dagster_home/dagster.yaml
run_coordinator:
  config:
    max_concurrent_runs: 5      # ← 改這個
```

⚠️ **改 `dagster.yaml` 要重啟容器才會生效**(不是 Reload code location)。

考量點:

| 想調大到 | 要先確認 |
|---|---|
| 10 | VM1 扛得住同時 10 個 SSH session 跟 10 支 Python 在跑嗎 |
| 更多 | SQL Server 的連線數與 BCP 併發能力;dbt 容器同時啟動的資源 |

**瓶頸通常在 VM1 跟資料庫,不在 Dagster。** 調大之前先看 VM1 的 CPU/IO。

---

### 調整 B:讓某個資產可以並行

目前每個資產的 pool 上限都是 1。要讓某個資產能同時跑多個分區:

**方法一:改該資產的 pool 名稱,讓多個資產共用一個池**(不建議,會互相排隊)

**方法二:在 `dagster.yaml` 給特定池獨立的上限**

```yaml
concurrency:
  default_op_concurrency_limit: 1
  pools:
    T_TXN_PS_fetch_ftp:
      max_concurrent: 3
```

> 語法依 dagster 版本而異,改之前先確認你的版本支援哪種寫法。

⚠️ **入庫節點(`database/*`)絕對不要放寬**,同一張表並行 BCP 會出事。
真的要放寬,只放寬下載/加密這類唯讀或寫不同檔案的節點。

---

### 調整 C:改某張表的重試次數

在 `table_mapping.py` 該表的設定裡:

```python
    "retries": 3,              # ← 改次數，0 代表不重試
    "retry_delay_sec": 60,     # ← 改間隔秒數
```

| 情況 | 建議 |
|---|---|
| 對方 FTP 常常抽風 | `retries: 5`,`retry_delay_sec: 300` |
| 失敗一定是資料問題,重試沒意義 | `retries: 0`,失敗直接讓人看到 |
| 檔案很大、跑很久 | 間隔調大,避免重試時前一次還沒清乾淨 |

---

### 調整 D:改 Run 層的重試

在 `sensors.py` 裡搜尋 `dagster/max_retries`,**有兩個地方**
(檔案 watcher 一份、db_sync sensor 一份):

```python
                tags={
                    "dagster/max_retries": "3",
                    "dagster/retry_strategy": "FROM_ASSET_FAILURE",
                },
```

| 策略 | 意思 |
|---|---|
| `FROM_ASSET_FAILURE` | 只重跑失敗的資產(**目前用這個,建議保持**) |
| `ALL_STEPS` | 整個 Run 從頭重跑(會造成資料重複) |

---

### 調整 E:改 dbt 的層級重試

```python
# assets.py::_run_dbt_levels
    max_retries = 2
    retry_delay = 30
```

dbt 失敗多半是 SQL 邏輯或資料問題,重試通常沒用。
**如果你發現 dbt 常常靠重試才成功,那是在掩蓋真正的問題**(例如上游資料還沒到齊),
應該去修相依關係而不是加重試次數。

---

### 調整 F:改 SSH 逾時

```python
# pipes_ssh_client.py
class PipesSSHClient(PipesClient, ConfigurableResource):
    ssh_host: str
    ssh_user: str
    ssh_key_path: str
    timeout_seconds: int = 7200        # ← 改這個（2 小時）
```

超過這個時間 Python 會直接砍掉 SSH,但**VM1 上的程序可能還在跑**,
造成「Dagster 說失敗,實際上檔案還在產生」的狀況。

**逾時常發生的話,優先考慮把工作拆小**(例如多檔分批),而不是一直調大。

## 三、改完怎麼驗證

| 改了什麼 | 怎麼驗證 |
|---|---|
| `dagster.yaml` | **重啟容器**,然後開一個 backfill 觀察同時有幾個 Run 在 STARTED |
| `retries` | 故意讓某個資產失敗(例如把檔案改名),看 Run 詳細頁有沒有重試紀錄 |
| Run 層 tag | 看 Run 詳細頁上方的 tag 區,應該看到 `dagster/max_retries` |
| pool 設定 | Deployment → Concurrency 頁面(依版本)可以看到各池的使用狀況 |

## 四、判斷「該調哪一個」的思路

| 症狀 | 該調的地方 |
|---|---|
| 積壓一堆檔案消化不完 | 先看 Runs 頁面:**QUEUED 很多** → 調 `max_concurrent_runs`;**沒有 QUEUED 但 sensor 一直沒派工** → 調 sensor 的 `max_files` |
| 同一張表的不同日期互相排隊 | 這是**設計行為**,不要動。要加速請改成一次處理多天的邏輯 |
| 常常逾時 | 先量 VM1 上實際耗時,再決定是調 timeout 還是拆批 |
| 失敗後沒重試 | 檢查該表的 `retries` 是不是 0 或沒填 |
| 重試了但每次都失敗 | 這是資料/設定問題,加重試次數沒用 |
