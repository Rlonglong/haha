# 06 · 新增一張 DB 直連同步表

**適用情境**:對方不給檔案,而是直接開資料庫給我們撈。

跟檔案線的差別:沒有 FTP、沒有檔規、沒有清洗,但**多了一道「解密再加密」**——
來源端的密文用對方的方式解開,再用我們的方式加密後才進我方資料庫。

---

## 流程

```
來源 DB ──撈取+解密──> VM1 暫存明文 CSV ──加密──> 加密 CSV ──BCP──> 我方 DB ──> 清除暫存
```

四個資產(固定都會建立):

| 資產 | 做什麼 |
|---|---|
| `file_system/<表名>_db_extract` | 連來源 DB 撈資料,用 `F_DecryptData` 解密,寫成明文 CSV |
| `file_system/<表名>_encrypted` | 用我們的方式加密 |
| `database/<表名>` | BCP 灌進我方資料庫 |
| `file_system/<表名>_cleanup` | 刪明文暫存、封存加密檔 |

> 明文只存在於 VM1 的暫存區,而且入庫成功後就會被刪掉。**失敗時檔案會留著方便查問題。**

---

## Step 1 · 在我方 SQL Server 建好目標表

- [ ] `dbo.T_NEW_ALERT`(或你在 `bcp_target` 指定的表名)
- [ ] 欄位型別要能容納**加密後**的長度(密文通常比明文長)

---

## Step 2 · 在 `db_sync/config.py` 新增設定

檔案位置:`dagster_workspace/dagster_code/db_sync/config.py`

```python
"T_NEW_ALERT": {
    "freq": "daily",                              # daily / monthly
    "source_db": "DDLQRMSV",                      # 來源資料庫名
    "source_table": "dbo.T_NEW_ALERT",            # 來源表（schema.table）
    "bcp_target": "T_NEW_ALERT",                  # 我方目標表，省略則同 key

    "decrypt_fields": ["ACCOUNT", "ID", "BIRTHDATE"],          # 來源端的密文欄位，用對方的 F_DecryptData 解
    "encrypt_fields": ["ACCOUNT", "ID"],          # 進我方 DB 前改用我們的方式加密
    "decrypt_key_env": "SOURCE_DECRYPT_KEY",      # VM1 .env 裡的金鑰變數名

    "sensor_watch_col": "NOTIFY_DATE",            # sensor 用來分批次的欄位
    # "notify_date_col": "NOTIFY_DATE",           # 撈資料的 WHERE 欄位，省略則同上

    "retries": 0,
    "retry_delay_sec": 60,
    "archive_dir": "T_NEW_ALERT_archive",         # ★必填★
},
```

### 幾個要注意的

| 設定 | 說明 |
|---|---|
| `archive_dir` | **必填**,不給會在載入時直接報錯。相對路徑會接在 `/run/media/root/D/data/` 之後 |
| `decrypt_fields` / `encrypt_fields` | 兩者不一定要相同。例如生日只需解密不需加密,就只放在 `decrypt_fields` |
| `sensor_watch_col` | sensor 靠這個欄位把資料分批。daily 取前 8 碼、monthly 取前 6 碼 |
| 表名與所有欄位名 | 都會經過白名單驗證(只能英數字底線),不合法在 Reload 時就會失敗 |
| `manual_only: True` | 加了就不輪詢來源 DB,只能手動跑 |

## Step 5 · 驗證

1. 手動跑 `file_system/T_NEW_ALERT_db_extract` 一個分區
   → 到 VM1 看 `~/db_sync/T_NEW_ALERT/` 有沒有明文 CSV,解密欄位是不是可讀的
2. 跑 `_encrypted` → 確認密文產生
3. 跑 `database/T_NEW_ALERT` → 查資料庫筆數,看 `bcp_error_logs`
4. 跑 `_cleanup` → 確認明文暫存已刪除、加密檔進了封存目錄
5. 看 sensor:**Automation → `db_sync_watcher_sensor`** 的 tick log

---

## Sensor 是怎麼判斷「資料到齊」的

檔案線是看檔案的修改時間,DB 線沒有這個東西,所以改看**筆數**:

```
每 5 分鐘查一次來源 DB 各批次的筆數
   ↓
筆數跟上次一樣？ → 否 → 重新計時
   ↓ 是
已經穩定超過 5 分鐘？ → 否 → 繼續等
   ↓ 是
觸發該分區的同步
```

相關參數在 `db_sync/config.py` 最上面:

| 參數 | 目前值 | 意義 |
|---|---|---|
| `DB_SYNC_STABLE_SECONDS` | `300` | 筆數要連續穩定幾秒才算到齊 |
| `DB_SYNC_STALL_WARN_SECONDS` | `7200` | 等超過幾秒還沒穩定就發警告 |

對方的批次寫得比較慢的話,把 `DB_SYNC_STABLE_SECONDS` 調大。

---

## ⚠️ 注意:月頻的 DB 同步表不在月批次 job 裡

`db_sync` 群組不屬於 `monthly_extract_load`,所以即使設 `freq="monthly"`,
`__MONTHLY_ASSET_JOB` 也不會涵蓋它(它會落在日批次 job 的選集內)。

**人工補跑請直接對資產操作**,不要靠批次 job。
