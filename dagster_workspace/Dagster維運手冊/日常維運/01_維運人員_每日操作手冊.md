# 01 · 維運人員 每日操作手冊

這份手冊是寫給每天負責看這套系統有沒有正常運作的同仁。

你**不需要**懂 Python、SQL 或 dbt。你要做的事情只有四件:**看狀態 → 判斷是不是真的壞了 → 該重跑的重跑 → 不該自己處理的通報出去**。

系統絕大多數時候會自己跑完,你多半只是確認一下。真的出問題時,這份手冊會告訴你怎麼判斷跟怎麼做。

---

## 先認識四個字

Dagster 的畫面上會一直出現這幾個詞,先有個印象就好:

| 畫面上的字 | 白話意思 |
|---|---|
| **Asset(資產)** | 一個處理步驟。像是「下載檔案」「加密」「灌進資料庫」,各自都是一個資產 |
| **Run(執行)** | 一次實際的執行紀錄。點進去可以看到過程 |
| **Materialize(實體化)** | 就是「執行這個步驟」的意思 |
| **Partition(分區)** | 資料的日期。`2026-08-01` 就是 8 月 1 日那一批資料 |

---

## 每天要看的三件事

### 步驟 1 · 先看有沒有失敗的執行

打開 Dagster 網頁,左邊選單點 **Runs**。這一頁會列出所有執行紀錄,最新的在最上面。

![Runs 總覽](./images/01_runs_overview.png)

你只要看 **Status** 那一欄的顏色:

| 顏色 / 文字 | 意思 | 你要做什麼 |
|---|---|---|
| 🟢 `SUCCESS` | 跑完了,沒問題 | 不用理它 |
| 🔵 `STARTED` / `STARTING` | 正在跑 | 不用理它。但如果**超過 2 小時**還在跑,請往下看步驟 3 |
| 🟡 `QUEUED` | 排隊中 | 正常。系統同時最多跑 5 個,其他的會排隊 |
| 🔴 `FAILURE` | **失敗了** | **往下看步驟 2** |
| ⚪ `CANCELED` | 被取消 | 通常是有人手動取消的,確認一下是不是自己人做的 |

看到紅色不用緊張——系統本來就會自己重試,很多問題會自己恢復。往下看怎麼判斷。

---

### 步驟 2 · 失敗了,看看是哪一個步驟失敗

點進那一筆紅色的 Run,會進到執行的詳細畫面。

![Run 詳細頁](./images/02_run_detail.png)

#### 先看它有沒有已經重試過

這裡有一件很重要的事:**系統遇到失敗會自己重試,通常要重試三次都失敗,才會真的變成紅色退出。**

所以你在畫面上看到同一個步驟出現好幾次(或是看到 retry 的標記),那是正常的自動重試,不是有人手動點了三次。

這也代表一件事:**你看到的紅色,是系統已經試過三次都失敗的結果。** 那種「網路抖一下」的暫時性問題,系統自己就處理掉了,根本不會走到你面前。所以紅色出現時,**先別急著再手動重跑一次**,先看 log 是什麼原因(步驟 3),再決定重跑有沒有意義。

#### 記下失敗的步驟名稱

在步驟清單裡找到紅色那一行,把名稱記下來。名稱會長這樣:

| 名稱樣式 | 代表哪個階段 |
|---|---|
| `file_system/XXX_fetch_ftp` | 從 FTP 下載檔案 |
| `file_system/XXX_named` | 套用欄位名稱 |
| `file_system/XXX_encrypted` | 加密 |
| `file_system/XXX_clean` | 資料清洗 |
| `database/XXX` | 灌進資料庫 |
| `file_system/XXX_archive_cleanup` | 封存清理 |
| `XXX`(名稱裡沒有斜線) | dbt 產出名單 |
| `export/XXX` | 匯出 CSV |

通報的時候會需要這個名稱,還有它的**分區日期**(也在這一頁上)。

---

### 步驟 3 · 看 log,判斷是什麼問題

![Log 區域](./images/03_run_logs.png)

#### ⚠️ 這裡有個很容易卡住的地方

**log 不會自動顯示失敗步驟的內容。你必須先「點選」你要看的那個步驟,右邊(或下方)才會出現它的 stdout / stderr。**

也就是說:

1. 在步驟清單裡,**用滑鼠點一下那個紅色的步驟**
2. 這時候才會載入它的 log
3. 沒有點的話,你看到的是別的步驟的輸出,或是根本一片空白

很多人第一次用會以為「log 壞掉了」,其實只是沒點到。**要看哪個步驟的訊息,就點哪個步驟。**

點好之後,在 log 裡找**紅色的錯誤訊息**,或直接搜尋 `❌` 這個符號。

#### 對照這張表判斷

| log 裡看到 | 意思 | 你可以做 | 要通報嗎 |
|---|---|---|---|
| `檔案未抵達` / `FileNotFoundError` | 對方的檔案還沒送到 | **等就好**,下一輪通常會自己補上 | 隔天還是沒有 → 通報 |
| `SSH 遠端執行失敗` | VM1 連不上,或上面的程式出錯 | 可以重跑一次看看 | 重跑還是失敗 → 通報 |
| `BCP` 相關錯誤 | 資料格式跟資料表對不上 | **不要重跑** | **直接通報開發人員** |
| `Timeout` / `逾時` | 檔案太大或網路太慢 | 可以重跑一次 | 連續三次 → 通報 |
| `找不到 XXX 的清洗邏輯` | 設定漏掉了 | **不要重跑** | **直接通報開發人員** |
| 其他看不懂的 | — | **先不要自己試** | 截圖通報 |

#### 判斷的大原則

**重跑只對「暫時性問題」有用**——網路不通、檔案還沒到、逾時這一類。

如果是「資料格式不對」或「設定漏了」,那是程式或資料本身的問題,**重跑一百次也是一樣的結果**,請直接通報,不要浪費時間。

再提醒一次:系統已經自動重試過三次了。你手動再重跑一次,只有在「你相信這幾分鐘內狀況已經改變」(例如對方的檔案剛剛才傳完)的時候才有意義。

---

### 步驟 4 · 需要重跑的時候

在 Run 詳細頁的右上角,可以找到重新執行的按鈕。

![重跑按鈕](./images/04_reexecute.png)

點開之後會有幾個選項,你會用到的是這兩個:

#### ✅ Re-execute from failure(從失敗處重跑)

**這是你九成的情況下該選的。**

它只會跑失敗的那一步,以及它後面還沒跑的步驟;前面已經成功的步驟不會重做。這樣既省時間,也不會把已經灌進資料庫的資料再灌一次。

#### ✅ Re-execute from selected(從指定步驟開始跑)

如果你要**從中間某一個步驟重新開始**,可以用這個。

用法是:**先在步驟清單裡點選你想開始的那個步驟**(可以是任何一個,不一定是失敗的那個),再選這個選項。系統就會從你選的那一步開始往下跑。

什麼時候會用到?例如開發人員請你「從清洗那一步再跑一次就好」,或是你發現某個中間步驟的產出怪怪的,想從那裡重來。

> 選這個之前,**建議先跟開發人員確認要從哪一步開始**。選錯步驟可能會跳過必要的處理。

#### ❌ Re-execute all steps(全部重跑)

**不要選這個。** 它會從第一步重頭跑,包含已經成功灌進資料庫的那一步——**資料會重複**。

## 想知道一個步驟會影響到誰(血緣圖)

有時候你會想知道:「這個步驟失敗了,會不會影響到後面的名單?」

Dagster 有一個**血緣圖(Lineage)**的畫面,可以看到一個步驟的**上游**(它要等誰跑完)跟**下游**(誰在等它)。

![血緣圖](./images/14_lineage_view.png)

最快的開啟方式:左邊選單點 **Catalog** → 搜尋你要看的步驟名稱 → 點進去 → 選上方的 **Lineage** 標籤。

詳細操作在 [02_開發人員_UI操作手冊 · 血緣圖](./02_開發人員_UI操作手冊.md#5-血緣圖lineage看一個步驟的上下游)有完整說明,你只要會「開起來看」就夠了。

**通報的時候如果能一併說「這個失敗會擋住下游的 OO 名單」,對開發人員很有幫助。**

---

### 步驟 5 · 確認偵測器還活著

系統靠幾支「偵測器(Sensor)」自動發現新檔案並開始處理。**如果偵測器停了,檔案到了也不會有人理它**,而且畫面上不會有任何紅色——這是最容易被忽略的狀況,所以每天要看一眼。

左邊選單 → **Automation**(或 **Sensors**)。

![Sensor 清單](./images/05_sensors_list.png)

你要確認兩件事:

**① 每一支的開關都是開的**

**② 最後執行時間(Last tick)是最近的**

| 偵測器名稱 | 它在做什麼 | 正常的最後執行時間 |
|---|---|---|
| `daily_file_watcher_sensor` | 找每日的新檔案 | 5 分鐘內(凌晨 0–6 點會是 30 秒內) |
| `monthly_file_watcher_sensor` | 找每月的新檔案 | 同上 |
| `db_sync_watcher_sensor` | 看對方資料庫的資料到齊了沒 | 5 分鐘內 |
| `default_automation_condition_sensor` | 上游好了就自動帶起下游 | 1 分鐘內 |

> **為什麼一般時段是 5 分鐘?** 這是刻意設計的。凌晨 0 點到 6 點是檔案密集進來的時段,所以掃得比較勤(30 秒一次);白天檔案少,改成 5 分鐘掃一次,避免一直去打擾 VM1。**所以白天看到「最後執行時間是 4 分鐘前」是完全正常的。**

**如果某一支的最後執行時間停在很久以前**(超過 30 分鐘),點進去看看有沒有紅色的錯誤,然後**通報開發人員**。

## 什麼情況要立刻通報

| 狀況 | 嚴重度 |
|---|---|
| 同一張表連續 3 次以上失敗 | 🔴 高 |
| 偵測器停止運作(最後執行時間超過 30 分鐘) | 🔴 高 |
| 整個網頁打不開,或畫面上顯示 code location 錯誤 | 🔴 高 |
| BCP 相關的錯誤 | 🟠 中 |
| 單次失敗,重跑之後就好了 | 🟢 低(記錄一下就好) |

**通報時請一併附上這四樣**,可以省下很多來回:

1. Run 頁面的截圖(或直接把網址複製給對方)
2. 失敗的步驟名稱(例如 `database/T_TXN_PS`)
3. 分區日期(例如 `2026-08-01`)
4. log 裡的紅色錯誤訊息——**請複製文字**,不要只截圖,開發人員需要搜尋關鍵字

---

## 有幾件事請不要做

這些操作會影響資料正確性,或是讓系統停止運作:

| 不要做 | 為什麼 |
|---|---|
| 關閉任何偵測器 | 關掉之後檔案到了也不會自動處理,而且畫面上不會有紅色提醒 |
| 選 `Re-execute all steps` | 資料會重複灌進資料庫 |
| 在 Launchpad 手動改參數送出 | 參數打錯會產生錯誤的資料 |
| 點 Reload code location | 那是開發人員改完程式才需要做的 |
| 刪除任何執行紀錄 | 之後就查不到問題是怎麼發生的了 |

**只要有一點猶豫,先截圖問開發人員**,不要自己試。問一句話的成本,遠比資料出錯低得多。
