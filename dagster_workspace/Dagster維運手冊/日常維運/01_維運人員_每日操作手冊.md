# 01 · 維運人員 每日操作手冊

**對象**:負責每天監看系統是否正常的人員。
**前提**:你**不需要**懂 Python、SQL 或 dbt。你要做的是「看狀態、判斷紅燈、重跑或通報」。

> 📌 本手冊的截圖請放在 `./images/` 資料夾,檔名照每張圖上方標註的名稱。
> 各版本 Dagster 的選單位置可能略有差異,以你畫面上的文字為準。

---

## 名詞對照(先記這四個就夠)

| UI 上的字 | 白話意思 |
|---|---|
| **Asset（資產）** | 一個處理步驟。例如「下載檔案」「加密」「灌進資料庫」各是一個資產 |
| **Run（執行）** | 一次實際的執行紀錄 |
| **Materialize（實體化）** | 「執行這個步驟」的意思 |
| **Partition（分區）** | 資料的日期。`2026-08-01` 就是 8 月 1 日那批資料 |

---

## 每日檢查流程(約 5 分鐘)

### 步驟 1:看今天有沒有失敗

打開 Dagster 網頁 → 左側選單點 **Runs**。

![Runs 總覽](./images/01_runs_overview.png)
> 📷 **要截的畫面**:左側選單點 Runs 之後的完整頁面
> 🔲 **框起來的地方**:
> 1. 左側選單的「**Runs**」項目(框住這個字)
> 2. 表格最左邊的「**Status**」欄位(整欄框起來)
> 3. 上方的狀態篩選器(通常寫著 `All runs` 或有一排 Success/Failure 標籤)

**判讀方式**:

| 顏色 / 文字 | 意思 | 你要做什麼 |
|---|---|---|
| 🟢 `SUCCESS` | 成功 | 不用管 |
| 🔵 `STARTED` / `STARTING` | 正在跑 | 不用管,但如果超過 2 小時還在跑 → 見步驟 4 |
| 🟡 `QUEUED` | 排隊中 | 正常,系統同時最多跑 5 個 |
| 🔴 `FAILURE` | **失敗** | **往下看步驟 2** |
| ⚪ `CANCELED` | 被取消 | 通常是人為取消,確認是不是自己人做的 |

---

### 步驟 2:失敗了,先看是哪一個步驟失敗

點進那筆紅色的 Run。

![Run 詳細頁](./images/02_run_detail.png)
> 📷 **要截的畫面**:點進一筆失敗的 Run 之後的頁面
> 🔲 **框起來的地方**:
> 1. 頁面上方的 **Run ID** 與 **狀態標籤**
> 2. 中間的**步驟清單**(每一行是一個資產,失敗的那行會是紅色)
> 3. 右下方的 **log 區域**

在步驟清單裡找到紅色那一行,記下它的名稱。名稱會長得像:

| 名稱樣式 | 代表哪個階段 |
|---|---|
| `file_system/XXX_fetch_ftp` | 從 FTP 下載檔案 |
| `file_system/XXX_named` | 套用欄位名稱 |
| `file_system/XXX_encrypted` | 加密 |
| `file_system/XXX_clean` | 資料清洗 |
| `database/XXX` | 灌進資料庫 |
| `file_system/XXX_archive_cleanup` | 封存清理 |
| `XXX`(沒有斜線) | dbt 產出名單 |
| `export/XXX` | 匯出 CSV |

---

### 步驟 3:看 log,對照下面的處理原則

在 log 區域找**紅色的 error 訊息**,或搜尋關鍵字 `❌`。

![Log 區域](./images/03_run_logs.png)
> 📷 **要截的畫面**:Run 詳細頁下方的 log 區塊,拉到有錯誤訊息的位置
> 🔲 **框起來的地方**:
> 1. log 區塊上方的**篩選列**(可以只看 ERROR 的那個下拉選單)
> 2. 一段紅色的**錯誤訊息**範例

**常見錯誤與處理原則**:

| log 裡看到 | 意思 | 你可以做 | 需要通報嗎 |
|---|---|---|---|
| `檔案未抵達` / `FileNotFoundError` | 對方檔案還沒送到 | **等**,通常下一輪會自己補上 | 隔天還是沒有 → 通報 |
| `SSH 遠端執行失敗` | VM1 連不上或腳本出錯 | 重跑一次(步驟 4) | 重跑仍失敗 → 通報 |
| `BCP` 相關錯誤 | 資料格式跟資料表對不上 | **不要重跑** | **直接通報開發人員** |
| `Timeout` / `逾時` | 檔案太大或網路慢 | 重跑一次 | 連續三次 → 通報 |
| `找不到 XXX 的清洗邏輯` | 設定漏了 | **不要重跑** | **直接通報開發人員** |
| 其他看不懂的 | — | **不要亂試** | 截圖通報 |

> ⚠️ **重要原則**:重跑只對「暫時性問題」(網路、檔案還沒到、逾時)有用。
> 如果是「資料格式不對」或「設定漏了」,重跑一百次也是一樣失敗,請直接通報。

---

### 步驟 4:重跑

在 Run 詳細頁的右上角找到重跑按鈕。

![重跑按鈕](./images/04_reexecute.png)
> 📷 **要截的畫面**:Run 詳細頁的右上角區域
> 🔲 **框起來的地方**:
> 1. 「**Re-execute**」按鈕(或寫著 Retry / 重新執行)
> 2. 點開之後的選單,特別是「**Re-execute from failure**」這一項

**一律選「Re-execute from failure」**(從失敗處重跑)。這樣只會跑失敗的那一步,前面成功的步驟不會重做,省時間也避免資料重複。

> ❌ **不要選** `Re-execute all steps`(全部重跑),那會把已經灌進資料庫的資料再灌一次。

---

### 步驟 5:確認偵測器還活著

左側選單 → **Automation**(或 **Sensors**)。

![Sensor 清單](./images/05_sensors_list.png)
> 📷 **要截的畫面**:Automation / Sensors 頁面的清單
> 🔲 **框起來的地方**:
> 1. 每一列左邊的**開關**(必須是開啟狀態)
> 2. 「**Last tick**」那一欄的時間

**應該要看到這幾支,而且全部都是開啟的**:

| 名稱 | 正常的最後執行時間 |
|---|---|
| `daily_file_watcher_sensor` | 5 分鐘內(凌晨 0–6 點是 30 秒內) |
| `monthly_file_watcher_sensor` | 同上 |
| `db_sync_watcher_sensor` | 5 分鐘內 |
| `default_automation_condition_sensor` | 1 分鐘內 |

**如果某一支的最後執行時間停在很久以前** → 點進去看 tick 紀錄有沒有紅色錯誤 → **通報開發人員**。

## 什麼情況要立刻通報

| 狀況 | 嚴重度 |
|---|---|
| 同一張表連續 3 次以上失敗 | 🔴 高 |
| sensor 停止運作(最後執行時間超過 30 分鐘) | 🔴 高 |
| 整個網頁打不開 / 顯示 code location 錯誤 | 🔴 高 |
| BCP 相關錯誤 | 🟠 中 |
| 單次失敗但重跑後成功 | 🟢 低(記錄即可) |

**通報時請附上**:
1. Run 頁面的截圖
2. 失敗的資產名稱(例如 `database/T_TXN_PS`)
3. 分區日期(例如 `2026-08-01`)
4. log 裡的紅色錯誤訊息(複製文字,不要只截圖)

---

## 你**不應該**做的事

| 動作 | 為什麼不行 |
|---|---|
| 關閉任何 sensor | 關掉之後檔案到了也不會自動處理 |
| 選 `Re-execute all steps` | 會讓資料重複灌進資料庫 |
| 在 Launchpad 手動改參數送出 | 參數打錯會產生錯誤資料 |
| 點 Reload code location | 那是開發人員在改完程式後才做的 |
| 刪除任何 Run 紀錄 | 之後查不到問題發生的經過 |

有疑慮的時候,**先截圖問開發人員**,不要自己試。
