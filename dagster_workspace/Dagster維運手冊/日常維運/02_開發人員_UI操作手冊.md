# 02 · 開發人員 UI 操作手冊

**對象**:會改設定檔、改 SQL、改 Python 的人。
**維運人員不需要看這篇**——這裡的操作大多會影響資料。

> 📌 截圖放在 `./images/`,檔名照每張圖上方標註的名稱。

---

## 1. Reload code location(最常用)

**什麼時候要做**:改了 `dagster_code/` 底下任何 `.py`、或改了設定檔之後。

左側選單 → **Deployment** → **Code locations** 分頁。

![Code location 頁面](./images/06_code_locations.png)
> 📷 **要截的畫面**:Deployment → Code locations 分頁
> 🔲 **框起來的地方**:
> 1. 「**Code locations**」分頁標籤
> 2. 該 location 那一列的**狀態**(正常是綠色 `Loaded`)
> 3. 最右邊的「**Reload**」按鈕(通常是一個轉圈箭頭圖示)

**Reload 之後一定要確認狀態變回綠色。** 如果變成紅色,點進去看 traceback——語法錯誤、設定值不合法都會在這一刻爆出來(這是刻意設計的「早失敗」)。

### 載入失敗的常見原因

| 錯誤訊息關鍵字 | 原因 |
|---|---|
| `IndentationError` | 手改程式時縮排跑掉(Tab 混空白) |
| `設定值不合法` | 表名/索引名/分區函式名不符合白名單格式 |
| `必須提供 archive_dir` | 開了 FTP 下載但沒給封存目錄 |
| `No such file or directory: .../manifest.json` | 新增 dbt 模型後沒重新產生 manifest |
| `AttributeError: ... has no attribute` | 用到這個 dagster 版本沒有的 API |

## 2. 手動執行單一資產

**什麼時候要做**:新增表/模型後的首次驗證、補跑某一天。

左側選單 → **Assets** → 用搜尋框找到目標資產 → 點進去。

![Asset 詳細頁](./images/07_asset_detail.png)
> 📷 **要截的畫面**:點進某個資產(例如 `database/T_TXN_PS`)之後的頁面
> 🔲 **框起來的地方**:
> 1. 右上角的「**Materialize**」按鈕
> 2. 中間的**分區狀態列**(一格一天,綠色=已完成、灰色=沒跑過、紅色=失敗)
> 3. 下方的 **Upstream / Downstream** 相依圖

點 **Materialize** → 會跳出分區選擇。

![選擇分區](./images/08_partition_picker.png)
> 📷 **要截的畫面**:點 Materialize 之後跳出的分區選擇視窗
> 🔲 **框起來的地方**:
> 1. **分區清單**(選你要跑的日期)
> 2. 下方的「**Launch**」/「**Materialize**」確認按鈕
> 3. 如果有「**Upstream**」相關選項,框起來——它決定要不要連上游一起跑

> ⚠️ **首次驗證新表時,請一個節點一個節點跑**,不要一次跑整條鏈。這樣才知道是哪一段有問題。

## 3. 補跑一段期間(Backfill)

**什麼時候要做**:補歷史資料、修完 bug 後重算一段期間。

在資產詳細頁的分區狀態列上,**拖曳選取多個分區** → 點 Materialize;或到 **Overview → Backfills** 建立。

![Backfill 建立](./images/09_backfill.png)
> 📷 **要截的畫面**:選取多個分區後跳出的 backfill 設定畫面
> 🔲 **框起來的地方**:
> 1. **選取的分區範圍**(起訖日期)
> 2. **要涵蓋哪些資產**的清單
> 3. 「**Submit**」按鈕

**注意事項**:

- 同時最多跑 5 個 Run(`dagster.yaml` 的 `max_concurrent_runs`)
- 同一個資產不會並行(每個資產有自己的 pool,上限 1),所以 backfill 是**一天一天排隊跑**
- dbt 模型是 `max_partitions_per_run=1`,每個分區各自一個 Run
- **補很長一段期間之前先想清楚**:BCP 是 append,重跑同一天可能造成資料重複

## 4. 重置 Sensor 的 cursor

**什麼時候要做**:想讓 sensor 重新處理已經處理過的檔案。

Sensor 用 cursor 記住「哪些檔案已經派過工」,格式是 `<時間戳>|<已處理清單>`。同一個檔案不會派第二次。

左側選單 → **Automation** → 點進該 sensor。

![Sensor 詳細頁](./images/10_sensor_detail.png)
> 📷 **要截的畫面**:點進 `daily_file_watcher_sensor` 之後的頁面
> 🔲 **框起來的地方**:
> 1. 右上角的**開關**與「**Reset cursor**」按鈕(可能在 ⋯ 選單裡)
> 2. **Tick history**(每次掃描的紀錄)
> 3. 點開某一筆 tick 之後的 log

**Reset cursor 會讓 sensor 把所有還在目錄裡的檔案重新派一次工。** 執行前先確認這是你要的——它可能一次觸發很多 Run。

想只重跑某一天,**用手動 Materialize 比較安全**。

## 5. 看 Sensor 為什麼沒抓到檔案

點進 sensor → Tick history → 點開最近一筆 tick 的 log。

正常會看到每張表的掃描結果:
```
[T_TXN_PS] 監控目錄: /data/fromFPP/T_TXN_PS (mode=ftp), 找到: ['T_TXN_PS_20260801012819.zip']
```

| log 裡看到 | 代表 |
|---|---|
| 沒有這張表的訊息 | 這張表的 `freq` 跟這支 sensor 不符,或設了 `manual_only` |
| `找到: []` | 目錄裡沒有符合副檔名的檔案(zip 表看 `.zip`,其他看 `.csv`) |
| `檔案 xxx 似乎還在寫入中` | 檔案 mtime 距現在不到 60 秒,下一輪會再試 |
| `一般時段，距上次執行僅 N 秒，略過` | 正常節流,見進階調整第 10 篇 |
| `❌ [xxx] FTP 列目錄失敗` | VM1 連 FTP 有問題 |

## 6. 查編譯後的 SQL

dbt 模型寫的是樣板語法,實際執行的 SQL 在 `target/`。

**方法 A:直接在 VM4 上看檔案**
```bash
cat /data/deploy/workspace/dagster_workspace/dbt_project/target/compiled/post_office_dbt/models/ATM_C2.sql
```

**方法 B:不等排程,自己編譯指定日期**
```bash
docker run --rm \
  -v /data/deploy/workspace/dagster_workspace/dbt_project:/app/workspace/dbt_project \
  -w /app/workspace/dbt_project \
  --network docker-compose_vm4-network \
  dai/dagster:v2.6 \
  dbt compile --select ATM_C2 --vars '{"target_date": "2026-08-01"}' --profiles-dir .
```

**方法 C:在 UI 的 Run log 裡看**
dbt 執行時固定帶 `--debug`,log 裡會印出實際 SQL。

## 7. 重新產生 manifest

**什麼時候要做**:新增/改名/刪除 dbt 模型或快照之後。**這步驟漏掉的話,Dagster 完全看不到你的新模型。**

```bash
docker run --rm \
  -v /data/deploy/workspace/dagster_workspace/dbt_project:/app/workspace/dbt_project \
  -w /app/workspace/dbt_project \
  --network docker-compose_vm4-network \
  dai/dagster:v2.6 \
  dbt parse --profiles-dir .
```

跑完再回 UI 做 **Reload code location**。

## 8. 兩個批次 Job

左側選單 → **Overview** → **Jobs**。

| Job | 內容 |
|---|---|
| `__DAILY_ASSET_JOB` | 所有日檔資產(排除月檔與 `manual_only` 的表) |
| `__MONTHLY_ASSET_JOB` | 所有月檔資產(排除 `manual_only` 的表) |

這兩個 job **沒有排程**,只給人工整批補跑用。日常運作靠 sensor。

## 9. 改完程式後的標準驗證流程

```
1. 語法檢查（在容器裡）
   python3 -m py_compile /app/workspace/dagster_code/*.py

2. 如果動到 dbt → 重新產生 manifest（見第 7 節）

3. Reload code location → 確認狀態是綠色

4. Assets 頁面 → 確認新資產出現，群組與分區類型正確

5. 手動 Materialize 單一分區 → 一個節點一個節點看 log

6. 確認實際結果：
   - 檔案線 → VM1 上的檔案、資料庫筆數、錯誤 log
   - dbt   → target/compiled 的 SQL、資料庫表內容
   - 匯出   → 輸出的 CSV 內容與編碼

7. 看 sensor tick log 有沒有掃到

8. 觀察一個完整週期（隔天早上再確認一次）
```

## 10. 危險操作對照

| 操作 | 風險 | 做之前 |
|---|---|---|
| Reset sensor cursor | 可能一次觸發大量 Run | 先確認目錄裡有幾個檔案 |
| Re-execute all steps | 資料重複灌入 | 幾乎都該改用 from failure |
| 大範圍 backfill | 佔滿執行佇列數小時 | 先算清楚分區數 |
| 改 `dagster.yaml` | 要重啟容器,期間全部停擺 | 挑離峰時段 |
| 改 `partition_function` 相關設定 | 動到資料庫分區結構 | 先在測試環境驗證 |
