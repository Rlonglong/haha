# 02 · 開發人員 UI 操作手冊

這份是寫給會改設定檔、改 SQL、改 Python 的同仁。

這裡面的操作**大多會影響資料**,所以維運人員不需要看這篇——他們照 [01 篇](./01_維運人員_每日操作手冊.md) 做就好。

---

## 1. Reload code location

**什麼時候要做**:改了 `dagster_code/` 底下任何 `.py`,或改了設定檔之後。

左邊選單 → **Deployment** → **Code locations** 分頁。

![Code location 頁面](./images/06_code_locations.png)

Reload 之後**一定要確認狀態變回綠色的 `Loaded`**。

如果變成紅色,點進去會看到完整的 Python traceback。這是刻意的設計——語法錯誤、設定值不合法、必填欄位漏掉,全部都會在這一刻爆出來,而不是等到半夜排程跑的時候才出事。

### 載入失敗的常見原因

| 錯誤訊息關鍵字 | 原因 |
|---|---|
| `IndentationError` | 手改程式時縮排跑掉(Tab 混到空白) |
| `設定值不合法` | 表名 / 索引名 / 分區函式名不符合白名單格式 |
| `必須提供 archive_dir` | 開了 FTP 下載但沒給封存目錄 |
| `No such file or directory: .../manifest.json` | 新增 dbt 模型後沒重新產生 manifest |
| `AttributeError: ... has no attribute` | 用到這個 dagster 版本沒有的 API |

## 2. 手動執行單一資產

**什麼時候要做**:新增表或模型後的第一次驗證、補跑某一天。

左邊選單點 **Catalog**,用搜尋框找到你要的資產,點進去。

![Asset 詳細頁](./images/07_asset_detail.png)

這一頁上你會用到:

- 右上角的 **Materialize** 按鈕
- 中間的**分區狀態列**——一格一天,綠色代表跑過了,灰色是還沒跑,紅色是失敗
- 下方的相依關係區塊(想看完整的血緣圖請看第 5 節)

點 **Materialize** 之後,會跳出分區選擇的畫面。

![選擇分區](./images/08_partition_picker.png)

### 分區怎麼選

有兩種方式,看哪個順手:

- **用拉的**:直接在分區列上拖曳,選出一段範圍
- **手動輸入**:在起訖欄位直接打日期,範圍大的時候比拉的準

### 「只跑還沒跑的」怎麼設定

畫面下方有一個勾選項:

> **Backfill only failed and missing partitions within selection**

**勾起來的話,就只會跑你選的範圍內「失敗過的」跟「從來沒跑過的」分區**,已經成功的不會重做。

補一段期間的資料時這個很好用——可以放心選一整個月,它只會補缺的那幾天,不會把整個月重灌一次。

### ⚠️ 這個版本沒有「連上游一起跑」的選項

有些 Dagster 版本可以在這裡勾「順便把上游也跑一遍」,**我們這個版本沒有**。

所以如果上游還沒跑,你要**自己先去把上游跑完**,再回來跑這一個。不確定上游是誰的話,用血緣圖看(第 5 節)。

> 💡 **第一次驗證新的表或模型時,請一個節點一個節點跑**,不要一次跑整條鏈。這樣出問題你才知道是哪一段。

## 3. 補跑一段期間(Backfill)

**什麼時候要做**:補歷史資料、修完 bug 之後重算一段期間。

在分區狀態列上拖曳選取多個分區,或到 **Overview → Backfills** 建立。

![Backfill 建立](./images/09_backfill.png)

### ★ 重點:用 Materialize 旁邊的那個箭頭

**Materialize 按鈕旁邊有一個下拉箭頭**(截圖裡框起來的地方),點開它會有其他選項,其中一個是:

> **Materialize unsynced**

**選這個,它只會跑「還沒同步」的分區**——也就是上游已經更新、但這個資產還沒跟上的那些。

直接點 Materialize 的話,是把你選到的全部丟出去;用 unsynced 就只處理真正需要處理的,不會一次送出一大批。範圍選得比較大的時候,養成用這個的習慣。

### 執行數量會被兩層限制擋住

就算你一次送出很多分區,實際同時在跑的不會失控:

- **同時最多 5 個 Run**(`dagster.yaml` 的 `max_concurrent_runs`)
- **同一個資產不會並行**(每個資產有自己的 pool,上限是 1)

所以 backfill 實際上是**一天一天排隊跑**的。送出一個月的量,它會慢慢消化,不會把 VM1 打爆。

### 送出之前先想一下

- dbt 模型是一個分區一個 Run(`max_partitions_per_run=1`),分區數就是 Run 數
- **BCP 是 append**,重跑同一天可能造成資料重複——所以優先用「只跑失敗與缺漏」或 unsynced,不要無腦全選

## 4. Sensor 的 cursor:讓它重新處理,或立刻掃一次

Sensor 用一個叫 **cursor** 的字串記住自己做過什麼。它長這樣:

```
1754380800.0|["T_TXN_PS_2026-08-01", "T_CUST_2026-08-01"]
```

拆開看是兩段:

| 段落 | 內容 | 作用 |
|---|---|---|
| `1754380800.0` | 上次**真的執行掃描**的時間戳 | 用來做時段節流 |
| `["T_TXN_PS_2026-08-01", ...]` | 已經派過工的「表名_日期」清單 | 用來去重,同一個檔案不會派兩次 |

左邊選單 → **Automation** → 點進該 sensor。

![Sensor 詳細頁](./images/10_sensor_detail.png)

這一頁可以直接**編輯 cursor**,也可以看 **Tick history**(每一次掃描的紀錄,點開有 log)。

### 為什麼白天感覺「很久才掃一次」

這是刻意的設計,有兩層節流:

| 時段(台灣時間) | 實際掃描間隔 |
|---|---|
| **00:00 – 05:59**(離峰,檔案密集進來) | **30 秒** |
| **06:00 – 23:59**(一般時段) | **5 分鐘** |

一般時段其實 sensor 每 30 秒還是會被喚醒一次,但程式會檢查「距離上次真的掃描有沒有滿 5 分鐘」,沒滿就直接跳過。所以你在 Tick history 上會看到很多這種紀錄:

```
一般時段，距上次執行僅 87 秒，略過。
```

**這是正常的,不是壞掉。**

### 💡 想立刻掃一次,不想等那 5 分鐘

節流是靠 cursor 前面那個時間戳算出來的。所以你只要**把 cursor 前面的時間戳刪掉,只留 `|` 後面的清單**:

```
改成 →  |["T_TXN_PS_2026-08-01", "T_CUST_2026-08-01"]
```

時間戳被當成 0,「距上次執行」就變成一個很大的數字,節流條件不成立,**下一個 tick(30 秒內)就會真的去掃**。

**而且後面的已處理清單有保留,所以不會把舊檔案重跑一遍。** 這是想立刻驗證某個設定改動時最方便的做法。

### 想讓它重新處理已經做過的檔案

那就要動後面那段清單:

- **只想重跑某幾個**:把清單裡對應的 `"表名_日期"` 項目刪掉,存檔
- **全部重來**:用頁面上的 **Reset cursor** 功能(通常在右上角的 `⋯` 選單裡),它會把整個 cursor 清空

> ⚠️ **Reset cursor 之前先確認目錄裡有幾個檔案。** 清空之後,所有還留在監控目錄裡的檔案都會被重新派工,可能一次觸發一大批 Run。
>
> 只想重跑某一天的話,**用手動 Materialize 比較安全**,不要動 cursor。

### 看 sensor 為什麼沒抓到檔案

點進 Tick history 最近一筆,展開 log。正常會看到每張表的掃描結果:

```
[T_TXN_PS] 監控目錄: /data/fromFPP/T_TXN_PS (mode=ftp), 找到: ['T_TXN_PS_20260801012819.zip']
```

| log 裡看到 | 代表 |
|---|---|
| 完全沒有這張表的訊息 | 這張表的 `freq` 跟這支 sensor 不符,或設了 `manual_only` |
| `找到: []` | 目錄裡沒有符合副檔名的檔案(zip 的表只看 `.zip`,其他看 `.csv`) |
| `檔案 xxx 似乎還在寫入中` | 檔案的修改時間距現在不到 60 秒,下一輪會再試 |
| `一般時段，距上次執行僅 N 秒，略過` | 正常節流,見上面 |
| `❌ [xxx] FTP 列目錄失敗` | VM1 連 FTP 有問題 |

## 5. 血緣圖(Lineage):看一個步驟的上下游

血緣圖會把「誰要等誰」畫成一張圖,是排查問題最快的工具:

- **Upstream(上游)**:這個資產要等哪些東西跑完才能跑
- **Downstream(下游)**:哪些東西在等這個資產

失敗的時候看一眼血緣圖,馬上知道「卡住的是誰」跟「會影響到誰」。

### 怎麼打開

有兩條路,結果一樣,挑順手的用。

**路線 A · 從圖上的節點進去**

如果你已經在某張圖上看到那個節點了(例如 Run 詳細頁、或另一張血緣圖),**點那個節點 → 選 `View in asset catalog`**,就會跳到那個資產的頁面。

![從節點進入 asset catalog](./images/15_view_in_asset_catalog.png)

**路線 B · 直接從左邊選單找**

左邊選單點 **Catalog** → 用搜尋框打資產名稱 → 點進去。

不確定完整名稱也沒關係,搜尋是模糊比對的,打 `T_TXN_PS` 就會把相關的節點都列出來。

### 進去之後選上方的 Lineage 標籤

進到資產頁面之後,**點上方的 `Lineage` 標籤**,血緣圖就出來了。

![Lineage 標籤](./images/16_catalog_lineage_tab.png)

![血緣圖](./images/14_lineage_view.png)

圖上可以做的事:

- **往上游追**:順著箭頭往回看,找到最源頭是哪個檔案或哪張表
- **往下游追**:看這個資產壞掉會擋住哪些名單、哪些匯出
- **點任一個節點** → 可以再 `View in asset catalog` 跳過去,一路追下去

### 什麼時候特別好用

| 情境 | 怎麼用 |
|---|---|
| 某個 dbt 模型沒資料 | 往上游追,看是哪一張來源表沒進來 |
| 要手動跑一個資產,但不知道上游跑完沒 | 看上游節點的狀態(這個版本不能自動連上游一起跑,得自己確認) |
| 某張表要停用 / 改結構 | 往下游追,先確認會影響到誰 |
| 新增了模型,想確認相依有沒有接對 | 看 `ref()` / `source()` 有沒有正確變成圖上的連線 |

> 💡 相依關係完全是靠 dbt 的 `ref()` 跟 `source()` 建立的。**血緣圖上少了一條線,通常代表 SQL 裡把表名寫死了**,而不是圖畫錯。

## 6. 查編譯後的 SQL

dbt 模型寫的是樣板語法,實際執行的 SQL 在 `target/`。

**方法 A · 直接在 VM4 上看**
```bash
cat /data/deploy/workspace/dagster_workspace/dbt_project/target/compiled/post_office_dbt/models/ATM_C2.sql
```

**方法 B · 不等排程,自己編譯指定日期**
```bash
docker run --rm \
  -v /data/deploy/workspace/dagster_workspace/dbt_project:/app/workspace/dbt_project \
  -w /app/workspace/dbt_project \
  --network docker-compose_vm4-network \
  dai/dagster:v2.6 \
  dbt compile --select ATM_C2 --vars '{"target_date": "2026-08-01"}' --profiles-dir .
```

**方法 C · 在 UI 的 Run log 裡看**
dbt 執行時固定帶 `--debug`,log 裡會印出實際 SQL。記得**要先點選那個 dbt 步驟**,才會載入它的輸出。

## 7. 重新產生 manifest

**什麼時候要做**:新增 / 改名 / 刪除 dbt 模型或快照之後。

**這一步漏掉的話,Dagster 完全看不到你的新模型。**

```bash
docker run --rm \
  -v /data/deploy/workspace/dagster_workspace/dbt_project:/app/workspace/dbt_project \
  -w /app/workspace/dbt_project \
  --network docker-compose_vm4-network \
  dai/dagster:v2.6 \
  dbt parse --profiles-dir .
```

跑完再回 UI 做 **Reload code location**。

## 8. 兩個批次 Job

左邊選單 → **Overview** → **Jobs**。

| Job | 內容 |
|---|---|
| `__DAILY_ASSET_JOB` | 所有日檔資產(排除月檔與 `manual_only` 的表) |
| `__MONTHLY_ASSET_JOB` | 所有月檔資產(排除 `manual_only` 的表) |

這兩個 job **沒有排程**,只給人工整批補跑用。日常運作靠 sensor。

## 9. 改完程式後的標準驗證流程

```
1. 語法檢查（在容器裡）
   python3 -m py_compile /app/workspace/dagster_code/*.py

2. 如果動到 dbt → 重新產生 manifest（第 7 節）

3. Reload code location → 確認狀態是綠色

4. Catalog 頁面 → 確認新資產出現，群組與分區類型正確

5. 用血緣圖確認上下游接對了（第 5 節）

6. 手動 Materialize 單一分區 → 一個節點一個節點看 log
   （記得要點選步驟才會顯示它的 stdout / stderr）

7. 確認實際結果：
   - 檔案線 → VM1 上的檔案、資料庫筆數、錯誤 log
   - dbt   → target/compiled 的 SQL、資料庫表內容
   - 匯出   → 輸出的 CSV 內容與編碼

8. 看 sensor tick log 有沒有掃到
   （想立刻看到結果就把 cursor 前面的時間戳清掉，見第 4 節）

9. 觀察一個完整週期（隔天早上再確認一次）
```

## 10. 危險操作對照

| 操作 | 風險 | 做之前 |
|---|---|---|
| Reset sensor cursor | 可能一次觸發大量 Run | 先確認目錄裡有幾個檔案;只想立刻掃的話改成清時間戳就好 |
| Re-execute all steps | 資料重複灌入 | 幾乎都該改用 from failure 或 from selected |
| 大範圍 backfill 直接 Materialize | 佔滿執行佇列數小時 | 改用 Materialize unsynced 或勾「只跑失敗與缺漏」 |
| 改 `dagster.yaml` | 要重啟容器,期間全部停擺 | 挑離峰時段 |
| 改 `partition_function` 相關設定 | 動到資料庫的實體分區結構 | 先在測試環境驗證 |
